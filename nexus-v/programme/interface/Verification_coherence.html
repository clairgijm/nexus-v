Exigences par tome

Contenu des fichiers d'Exigences importés, rangé par tome dans nexus-v.db. C'est sur ces exigences que porte la vérification.

En rouge : exigences hors scope ; en vert : déjà qualifiées. En bleu : exigences ajoutées ou modifiées à la main ; barrées : supprimées (ignorées par la vérification). Le prochain import du tome écrase ces modifications.

Fiches d'Essai

Exigences testées par les Fiches d'essai chargées (XML et Excel, chacune de la plateforme choisie à son import), rangées par tome de l'exigence : une ligne par exigence et par test case.

Tables de la base

Le contenu de la base, une table par onglet. Les modifications sont directes et enregistrées tout de suite : seuls les liens entre tables sont contrôlés. Un prochain import ou chargement peut les écraser.

Toute la base (tables et contenu) dans un fichier .sql, à garder en sauvegarde.

STDHL

Exigences citées par les STDHL chargés, avec le test (fiche SYS_) demandé pour chacune : une ligne par exigence et par test (une exigence peut donc revenir plusieurs fois).

En bleu : lignes ajoutées ou modifiées à la main ; barrées : supprimées (ignorées par la vérification). Elles restent quand le STDHL est relu.

Répartition des exigences par tome

Délégation par tome et par plateforme

Exigences (hors supprimées) de chaque tome, par plateforme de délégation, selon le fichier d'exigences. Un clic ouvre le tome dans la page Exigences par tome.

IADT par tome

Exigences (hors supprimées) de chaque tome : par IADT pour celles à qualifier dans la release, puis celles déjà qualifiées et celles hors scope (colonne « Validation releases »).

Tomes par plateforme

Exigences (hors supprimées) déléguées à chaque plateforme, par tome. Un clic sur un tome l'ouvre dans la page Exigences par tome.

IADT par plateforme

Exigences (hors supprimées) déléguées à chaque plateforme : par IADT pour celles à qualifier dans la release, puis celles déjà qualifiées et celles hors scope (colonne « Validation releases »).

Couverture par les fiches d'essai, par plateforme

Exigences à qualifier déléguées à chaque plateforme dans les plans d'acceptation, couvertes ou non par ses fiches. Un clic sur une part liste ses exigences.

État des tests, par plateforme

Exigences couvertes par les fiches de chaque plateforme : PASSED si tous leurs tests sont passés, FAILED si l'un a échoué, Non exécuté sinon (les fiches Excel des autres plateformes n'ont pas de résultat). Un clic sur une part liste ses exigences.

Gestion des fichiers

Chaque fichier chargé est conservé dans fichiers-references/ sous le nom « n°_nom du fichier », et leur liste dans nexus-v.db. Cocher les fichiers à utiliser pour la vérification.

Configuration

Paramètres enregistrés dans config.json ; releases, tomes, plateformes, IADT et MOC, fichiers, exigences et plans gérés dans la base SQL, sauvegardée dans nexus-v.db. Les modifications de tous les onglets sont enregistrées ensemble.

Dossier des fichiers importés

Dossier où NEXUS-V conserve une copie de chaque fichier importé, dans un sous-dossier par type de fichier (nommé dans l'onglet de ce type). Le changement s'applique immédiatement, avec le bouton « Utiliser ce dossier ».

Processus retenu pour la release

Cliquer sur Plan d'acceptation ou STDHL pour le retenir (vert) ou non (gris) ; les Exigences et les Fiches d'essai font toujours partie du processus. NEXUS-V ne vérifie que les étapes retenues. Enregistré avec le bouton « Enregistrer la configuration ». Le STDHL ne peut plus être retenu une fois des fiches d'essai chargées.

Format 2 : un document pour tous les STDHL

Lu à l'import et par la vérification avant import. Chaque test est un titre « nom : titre » ; ses exigences associées sont la liste qui suit leur libellé (la fin de la liste termine les exigences) ; sa couverture est l'ensemble des exigences citées dans les phases de ses testcases, et les deux doivent être identiques (sinon, le fichier est refusé). Les libellés sont reconnus sans tenir compte des majuscules ni des accents.

Balises XML

Balises lues dans le fichier : un test contient des test-cases, qui contiennent les exigences testées, séparées par des virgules dans une même balise. Chaque information est le texte placé entre l'ouverture et la fermeture de sa balise. Quand une balise change, les fichiers déjà chargés sont relus.
